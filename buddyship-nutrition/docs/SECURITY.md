# SECURITY — セキュリティ要件

- 文書版: **v2.0 ドラフト(承認待ち)**
- 原則:**既定で拒否、DB で判定、最小権限、最小収集、記録は残すが中身は残さない。** 管理者にも健康データの包括閲覧権限を与えない。

## 1. 脅威と対策

## 2. 認証・JWT・セッション

| 項目 | 方針(仮) |
|---|---|
| ログイン | 方式は **[未決 D-04]**。高齢者がメールを使えない可能性があるため、事業所での初期設定支援を前提とする |
| MFA | スタッフ・管理者は TOTP 必須。判定関数で `aal2` を確認 |
| アクセストークン | Supabase Auth の JWT。有効期限は短め(既定 1 時間を目安に確認・調整) |
| JWT 検証 | Edge Function は JWT 検証を有効にし、関数内でも `auth.getUser()` で再確認。DB では `auth.uid()` / `auth.jwt()` |
| リフレッシュトークン | ローテーション有効、再利用検知(Supabase の設定項目を確認して記録) |
| 利用者のセッション | 本人の端末では長めに保持(再ログインの負担を下げる)。期間は D-04 と合わせて決定 |
| スタッフのセッション | 共用端末を想定し、無操作 15 分で自動ログアウト(仮)、最長 12 時間で再ログイン(仮) |
| ログアウト時 | トークン破棄、メモリ上のクエリキャッシュ消去、Service Worker のランタイムキャッシュ消去 |
| 権限の即時性 | 同意・割当・ロールは JWT に入れず毎回 DB で判定 |

## 3. 認可(要約)

- 判定はすべて DB(RLS と SECURITY DEFINER 関数)で行う。画面の出し分けは利便性のためだけ。
- スタッフ:担当割当 **かつ** 該当スコープの同意 **かつ** 同一組織 **かつ** aal2。
- 代理入力:データ種別ごとの `*:write` スコープが別途必要。
- 管理者:アカウント・割当・利用量・監査ログのみ。健康データにはアクセスできない。
- 詳細は [DATABASE.md §4](./DATABASE.md)。

## 4. service role キー

- 使用は `delete-account`・`admin-invite-user`・`purge-expired-images` の 3 関数に限定。
- 各関数で対象(user_id・パス)を確定させてから、1 か所で生成したクライアントを使う。
- CI で参照箇所を検査し、許可リスト外にあれば失敗させる。
- フロントの環境変数は `VITE_SUPABASE_URL`・`VITE_SUPABASE_ANON_KEY` のみ。

## 5. 入力値・画像の検証

- すべての API 入力を Zod で検証(`.strict()`、文字数・数値範囲・列挙値)し、DB 側でも CHECK 制約と RPC 内検証で二重に守る。
- 画像:端末で長辺 1600px(仮)に縮小し WebP/JPEG に再エンコード(EXIF・GPS 除去)。サーバーでサイズ・マジックバイト・寸法・デコード可否を検証(Deno での実装は R-03)。
- 日付:摂取日は未来不可、遡及は D-30 の期間内。

## 6. レート制限・AI 費用上限

| 対象 | 上限(仮) |
|---|---|
| AI 解析:呼出者あたり 1 分 | 3 回 |
| AI 解析:利用者あたり 1 日(本人+代理の合計) | 10 回 |
| AI 解析:スタッフあたり 1 日 | 60 回 |
| AI 解析:組織あたり 1 か月 | 3,000 回(80% で管理者に通知、100% で停止) |
| エクスポート:利用者あたり 1 日 | 5 回 |
| RPC 全般 | Supabase の API 制限に加え、書き込み RPC に呼出者あたりの分単位上限(仮 60 回/分) |
| Auth | Supabase Auth のレート制限設定を確認し記録 |
| プロバイダ側 | AI プロバイダのコンソールで月額の支出上限を設定 |

カウンタは `insert ... on conflict do update ... returning` で原子的に加算し、上限超過時は AI を呼ばない。管理者は AI を即時停止できる(`ai_enabled`)。

## 7. 個人情報・法令(要専門家確認)

技術者による整理であり法的判断ではない。**試験開始前に専門家の確認が必要 [未決 D-20]。**

- デイサービス利用者の健康関連情報の扱い。個人情報保護委員会・厚生労働省「医療・介護関係事業者における個人情報の適切な取扱いのためのガイダンス」の適用範囲の確認。
- 要配慮個人情報(病歴等)に当たる情報を収集しない設計にしている(病名・介護度を持たない)が、食事・体組成データと介護サービス利用の事実の組合せの扱いを確認。
- 厚生労働省「医療情報システムの安全管理に関するガイドライン」等への準拠要否の確認。
- 介護記録としての保存義務と、利用者による削除権の関係(削除してよい範囲)。
- AI プロバイダへの画像送信:委託か第三者提供か、外国にある第三者への提供に当たるか。プロバイダのデータ保持期間・学習利用の有無・データ処理契約の確認(D-01)。
- 同意能力が十分でない利用者の扱い(D-26)。
- 医療機器プログラム該当性:診断・治療・予防を目的とする表示をしない。

## 8. ログ

- 許可:request_id、関数名、ステータス、所要時間、ハッシュ化 user_id、AI のモデル名・トークン数、エラーコード。
- 禁止:氏名・表示名・メール・電話、画像・画像パス、食品名、量、身体値、AI 応答、JWT、APIキー。
- 共通ロガーに許可キーのホワイトリストを持たせる。`console.*` の直接使用を lint で禁止。
- 監査ログ(`audit.logs`)は追記専用。UPDATE/DELETE 権限を誰にも与えない。

## 9. 配信・フロントエンド

- CSP(例):`default-src 'self'; img-src 'self' blob: data: https://<project>.supabase.co; connect-src 'self' https://<project>.supabase.co; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`(`unsafe-inline` の要否は確認)。
- HSTS、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Permissions-Policy: camera=(self), geolocation=(), microphone=()`。
- ヘッダを設定できる配信先が必要 **[未決 D-03]**。
- Service Worker はアプリ殻のみキャッシュ。`/rest/`・`/functions/`・`/storage/` はネットワークのみ。

## 10. 秘密情報

- `.env*` は `.gitignore`(`.env.example` を除く)。`.env.example` はキー名と説明のみ。
- AI キー・service role キーは Supabase の Edge Function Secrets と GitHub Actions の Environment Secrets(デプロイ用、承認後に設定)のみ。
- GitHub のシークレットスキャンとプッシュ保護の有効化(リポジトリ設定、要確認)。
- **このリポジトリは GitHub Pages で全体を公開する設定になっている [未決 D-00]。** 文書・コードが公開されても困らない内容に限り、秘密・内部ホスト名・実データを含めない。

## 11. バックアップ・復元

| 項目 | 方針(仮) **[未決 D-31]** |
|---|---|
| DB | Supabase の自動日次バックアップ(Pro 以上で保持期間あり)。PITR アドオンの要否を RPO で判断 |
| 追加の論理バックアップ | 日次で `pg_dump`(スキーマ+データ)を暗号化し、Supabase とは別の国内保管先へ。保管先・暗号鍵の管理者は D-31 |
| Storage(画像) | DB バックアップに含まれない。短期保持の補助データのため、バックアップ対象外とする案 |
| Auth | `auth` スキーマは DB に含まれる。復元後にログインできることを訓練で確認 |
| 目標 | RPO 24 時間 / RTO 1 営業日(仮) |
| 削除との関係 | アカウント削除後もバックアップには保持期間中残る。プライバシーポリシーに明記。復元時は「復元後に削除済みアカウントを再削除する」手順を用意(削除記録を監査ログから取得) |
| 訓練 | Sprint 4 に staging で復元訓練(復元 → pgTAP → 件数・整合性チェック → 削除済みアカウントの再削除)|
| 権限 | バックアップの取得・復元ができる人を限定し、作業を記録 |

## 15. 食事記録の実装で確認したこと(Sprint 2)

- 食事のテーブルは RPC 経由のみ。権限(本人・担当+同意・MFA・組織)は DB 関数で毎回判定し、同意撤回後は同じセッションのまま拒否(pgTAP・結合・E2E で確認)。
- 栄養値・入力者・登録日時・場所はクライアントから受け取らない(余分なキーを拒否)。AI 由来の明細は解析記録にある推定量と照合し、AI 推定値の改ざんを防ぐ。
- 画像:非公開の Storage、パス形式の検査、本人フォルダ、中身(先頭のバイト)と大きさの検証、閲覧は本人のみで監査あり、キャッシュさせない。スタッフには画像のパスを返さない。
- 残る点:Storage を直接読む操作(本人が自分の画像を読む、代理撮影したスタッフが自分のアップロードを読む)は、ポリシーで制御されているが 1 件ずつの監査には残らない。期限切れ画像の自動削除は未実装。

## 14. 栄養情報の安全(2026-11-10 追加)

Phase 1 は**管理栄養士が常勤していない前提**で開発する。誤った栄養情報や、診断・指導と受け取られる表示は、利用者(高齢者)の健康に害を与えうるため、セキュリティと同じ重さで扱う。要件は PRD §1.1 の SAFE-1〜8。

| 脅威 | 対策 | 自動テスト |
|---|---|---|
| AI が疾患・状態(低栄養・サルコペニア等)を判定する | AI の出力スキーマは食品名・提供量・確からしさ・料理か食材かだけ(`.strict()` で他の項目を拒否)。AI に文章を生成させない。AI の出力は候補表示にしか使わない | AI 出力の検証テスト(Sprint 2)、画面文言の検査 |
| 個人別の目標量・食事制限・治療的な指導が表示される | 目標量・制限を保存する列・画面を作らない。画面文言の自動検査(`app/src/safety-copy.node.test.ts`)で、判定・指示の言い回しを禁止 | 画面文言の検査 |
| 不完全な記録が 1 日の総摂取量として表示される | 集計名は「記録済みの自宅食事の推定摂取量」だけを使い(`packages/nutrition/src/daily.ts`)、未記録・デイサービスの食事を含まないことを注記する。未記録の食事がある日は平均に使わない | 記録状況 64 通りのテスト |
| 構成食材が不明な料理・要確認の食品が精密な値に見える | 要確認の明細は合計に入れず、構成不明・要確認を含む食事は「約」付きのおおよその表示(`composition.ts`) | `composition.test.ts` |
| Tr(微量)が「0」と表示され、測定上のゼロと区別できない | 元の表記を保持し、Tr は「微量」と表示 | `calc.test.ts`・実データのテスト |
| 推定値が正確な値と受け取られる | 「推定」と「実際とは差がある」旨を必ず表示 | 表示文言のテスト |
| 成分表の列の取り違え・表記の読み違え(例:kJ を kcal と扱う、`-` を 0 と扱う) | 列の対応を公式 Excel(SHA-256 照合)で検証。想定外の表記は取込を止める。未測定は 0 にしない | `packages/nutrition` のテスト(全 2,538 食品) |
| エネルギーの再計算による公表値とのずれ | エネルギーは成分表の公表値(`ENERC_KCAL`)を使い、P/F/C から再計算しない | 再計算値と一致しないことを確かめるテスト |
| 出典・版が分からず、値の根拠を確かめられない | 出典表記・版・正誤表の反映日を画面に表示。食事明細に成分値・成分表の版・計算規則の版を保存 | 出典表示のテスト |
| 計算規則が画面や DB に散らばり、監修・修正ができない | 規則を `packages/nutrition` に集約し、規則の版(`NUTRITION_RULES_VERSION`)を持つ | — |

### 14.1 本番公開・実利用者への提供の条件

本番公開と実利用者への提供は、**個人情報保護・栄養情報の適切性・業務運用**の確認がすべて完了してから行う(PRD §10.1)。それまでは、ローカル・検証環境と合成データだけで開発・テストする。確認の結果(誰が・いつ・何を確認したか)は記録に残す。
