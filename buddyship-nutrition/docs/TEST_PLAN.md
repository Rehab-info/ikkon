# TEST_PLAN — テスト計画

- 文書版: **v2.0 ドラフト(承認待ち)**
- **テストデータは合成データのみ。** 実利用者のデータ・写真を開発・テストに使わない。精度検証用の写真は、スタッフが自分で用意・計量した料理など、権利と出所が明確なものに限る(D-14)。
- AI は単体・統合・E2E では**モック**。実 API は精度検証のみで、件数と費用の上限を事前承認。

## 2. 単体テストの重点

- **栄養計算**:提供量 × 食べた割合(0%・100%・端数)、複数明細、丸め境界、TS と SQL の結果一致(同じケース表を両方で実行)。
- **欠測判定**:3 区分の組合せ(recorded/skipped/dayservice/未記録 の 4^3 = 64 通り)で `complete` と表示文言が正しいこと。未記録が 0 として合計・平均に入らないこと。平均の分母が完全日数であること。
- **日付**:Asia/Tokyo の 0:00 境界、遡及期間の境界、未来日の拒否、摂取日時と登録日時が別に保存されること。
- **AI 出力検証**:栄養値キー混入 → 拒否、21 件 → 拒否、提供量 0・負数・2001 → 拒否、未知キー → 拒否、`is_food_image=false` → 手入力誘導。
- **画像**:拡張子偽装、5MB 超、寸法超過、破損、0 バイト。
- **ロガー**:許可外のキー(食品名・体重など)が出力されないこと。

※1 自分が代理入力した記録の確認表示の扱いは D-07。

追加ケース:
- スタッフが `grant_staff_consent` を自分宛てに呼ぶ → 拒否。管理者が呼ぶ → 拒否。
- 担当割当のない staff への同意付与 → 拒否。
- 割当解除 → 該当同意が自動撤回される(D-07 決定後)。
- スタッフが本人入力の食事を `update_meal` → 拒否。自分の代理入力を期限後に修正 → 拒否。
- `save_meal` に `location: "dayservice"` 等 → 拒否(API と DB の両方)。DB 直接で `location` を変える → 拒否。
- 栄養値・`recorded_at`・`entered_by` を payload に含める → 拒否(`.strict()`)。DB に直接 INSERT → 拒否。
- `ai_estimated_served_g` を解析結果と異なる値で送る → 拒否。
- `meal_items.member_id` の偽装 → 拒否(トリガー)。
- 記録ありの区分に `skipped` を設定 → 409。
- Storage:他人のフォルダへの upload/download/list → 拒否。`meals:write` を持つスタッフが担当利用者のフォルダへ upload → 許可、撤回後 → 拒否。`meals:read` のみのスタッフが画像取得 → 拒否(D-09)。上書き → 拒否。
- user_metadata に `role: admin` を書いても権限が変わらない。
- 監査ログ:全ロールで UPDATE/DELETE 拒否。スタッフの閲覧・代理入力・拒否が記録される。`metadata` に健康データの値がない。
- 管理者の `admin_list_audit_logs` の結果に健康データの値が含まれない。

## 4. カタログ検査(pgTAP)

- `public`・`audit`・`private` の全テーブルで RLS 有効。
- SECURITY DEFINER 関数はすべて `search_path` 固定、`PUBLIC` に EXECUTE なし。
- ビューはすべて `security_invoker = true`。
- `anon` ロールが利用者データのテーブルに権限を持たない。
- `authz`・`audit`・`private` が PostgREST の公開スキーマに含まれない(設定ファイルの検査)。

## 5. レート制限・費用上限

- 分・日・月の境界(JST 0:00、月末)。
- 10 件の同時リクエストで上限を超えて加算されない(原子性)。
- 上限到達・AI 停止中に AI アダプタが呼ばれない(モックの呼び出し回数で確認)。
- 本人+代理入力の合計で利用者の日次上限が効く。

## 6. その他の自動セキュリティテスト(CI)

- ビルド成果物に `service_role`・AI キーの書式の文字列がない。
- service role の参照が許可リスト内のファイルのみ。
- 依存関係の既知脆弱性検査(`npm audit` 等、重大度の閾値は Sprint 1 で決定)。
- `.env` 系ファイルがコミットされていない。

## 7. E2E シナリオ

| ID | シナリオ |
|---|---|
| E-01 | 本人:ログイン → はじめての同意 → 写真 → AI 候補(モック)→ 提供量を変更 → 食べた割合「半分」→ 保存 → ホームの記録状況と「記録した食事の合計」に反映 |
| E-02 | 本人:昼を「デイサービスで食べた」、夕を未記録 → ホームで「1日の合計」と表示されない、未記録の表示がある |
| E-03 | 本人:「食べなかった」を設定 → 完全日になる → 平均の日数に含まれる |
| E-04 | 本人:AI 失敗(モック)→ 手入力で記録 |
| E-05 | 本人:昨日の食事を遡及入力 → 摂取日=昨日、登録日時=今 |
| E-06 | スタッフ:`meals:write` で代理入力 → 本人画面で「スタッフ入力」と表示 |
| E-07 | 本人が `meals:write` を撤回 → スタッフの次の保存が拒否され、画面のデータが破棄される |
| E-08 | スタッフ:InBody 代理入力 → 本人のグラフに反映 |
| E-09 | スタッフ:ダッシュボードで同意のない列が「同意なし」表示 |
| E-10 | 管理者:利用者・スタッフ登録、割当 → 健康データの画面が存在しない・URL 直打ちで拒否 |
| E-11 | 本人:エクスポート → 内容確認、アカウント削除 → 再ログイン不可・データ・画像削除 |
| E-12 | スタッフ:無操作で自動ログアウト、ログアウト後に「戻る」で前の画面のデータが出ない |
| E-13 | 文字サイズ「とても大きく」で主要画面が崩れない(320px 幅含む) |
| E-14 | オフライン時にアプリ殻とオフライン表示(データは出ない) |

## 8. 栄養推定精度検証(Sprint 4)

- データセット:計量済みの家庭料理の写真 50〜100 枚(合成・自前撮影)。正解 = 食品成分表の食品と提供量。
- 指標:食品 Top-1/Top-5 一致率、提供量の絶対誤差率(中央値・90 パーセンタイル)、エネルギー誤差率(正解の食品・量から計算した値との比較)、料理の種類別の傾向(汁物・混ぜご飯・嚥下調整食など)。
- AI 解析は 1 枚 1 回 × 候補プロバイダ数。**総件数と費用の上限を事前に提示し、承認後に実行。**
- 合否基準は試験前に別途合意する。

## 9. 復元訓練(Sprint 4、staging)

1. 合成データを投入した staging でバックアップを取得。
2. 別プロジェクトに復元。
3. pgTAP 全件、件数・合計値の一致を確認。
4. 削除済みアカウントの再削除手順を実行。
5. 所要時間を記録し、RTO と比較。
