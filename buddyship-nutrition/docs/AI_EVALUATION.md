# AI_EVALUATION — 食事写真の AI プロバイダ比較(準備)

- 文書版: **v0.1 ドラフト(承認待ち)**/Sprint 3
- 関連: DECISIONS D-01(AI プロバイダ)・D-19(食品番号への対応付け)・D-36(本書の予算案)、SECURITY §6(AI への送信)、PRD SAFE-1〜8
- **この段階では有料の AI API を呼ばない。** 実行できるのは mock(開発用の仮の解析。外部に送信しない・費用なし)だけ。

## 1. 目的

自宅の食事の写真から「何を・どれだけ」を推定する AI を、同じデータ・同じ指標で比べ、D-01(プロバイダの選定)の判断材料にする。
栄養値は AI に出させない(成分表と packages/nutrition で決定的に計算する)。比べるのは **食品の識別と量の推定** と、その結果としての栄養の誤差・処理時間・費用。

**前提(変えない)**:AI が生成した食品候補は自動的に確定しない(Sprint 3)。画面では先頭の候補を「AI の候補」として示し、利用者・スタッフが「これで合っている」を押すか、別の候補を選んだときだけ確定する。評価では「確かめずに先頭の候補を採ったら」の精度を測り、利用者が選ぶ必要のある割合(要確認率)を別に測る。

## 2. 候補

| 候補 | 確認すること(評価開始時に公式資料で確認し、本書に日付と出典を書く) |
|---|---|
| OpenAI(画像入力に対応したモデル) | 日本のデータの扱い・学習への利用の有無・保存期間、構造化出力(JSON スキーマ)、料金、リージョン |
| Google Gemini(同上) | 同上 |
| その他(Anthropic Claude など、画像入力に対応したもの) | 同上 |

- モデル名・料金・データの取り扱い条件は変わるため、**本書には書かない**(古い値で判断しないため)。評価を始める日に各社の公式資料を確認し、`scripts/ai-eval/prices.json`(コミットしない)と結果の報告書に、確認日と出典 URL を添えて記録する。
- 契約・有料プランの申込みは行わない(承認後に、利用者を代表する事業者として判断)。

## 3. データセット(30〜50 食)

| 項目 | 内容 |
|---|---|
| 食事 | スタッフ・協力者が用意した **自宅の食事**(朝・昼・夕・間食)。和食中心、料理(肉じゃが・みそ汁など構成食材のあるもの)を半分以上 |
| 正解 | 食品ごとに **秤量した提供量(g)** と、成分表の食品番号(八訂増補2023)。調理油・調味料は使った量を量る |
| 撮影 | 家庭用のスマートフォン(iPhone・Android 各 1 台以上)、条件を変える(室内灯/自然光、白い器/柄の器、真上/斜め上)。撮影条件を `conditions` に記録 |
| 含めないもの | **利用者の実データ・利用者が撮った写真**(開発・評価に流用しない)、顔・郵便物・薬袋・住所が分かるもの |
| 形式 | `scripts/ai-eval/dataset.ts` の `EvalDataset`(Zod で検査)。`contains_member_data: false` が必須。画像はリポジトリにコミットしない(`scripts/ai-eval/data/` は .gitignore 済み) |
| 正解の確認 | 食品番号の付け方は、外部管理栄養士のスポット監修(D-33)の対象に含める |

`scripts/ai-eval/sample-dataset.json` は形式を示す架空の 2 食で、評価には使わない。

## 4. 指標

| 指標 | 定義(`scripts/ai-eval/metrics.ts`) |
|---|---|
| 食品の識別 | 予測の先頭の候補の食品番号が正解と一致した数で、適合率・再現率・F1。1 つの正解には 1 つの予測だけを対応させる |
| 重さの推定 | 一致した明細の「予測の提供量 − 秤量値」の絶対誤差の中央値(g)、相対誤差の中央値・平均 |
| 要確認率 | 先頭の候補が決まらない(別名が複数の食品に当たる・辞書にない・確からしさが低い)明細の割合。高いほど利用者の操作が増える |
| 栄養の誤差 | 1 食ごとのエネルギー・たんぱく質・脂質・炭水化物について、予測(先頭の候補 × 予測量)と正解(秤量値 × 成分表)の差の絶対値の中央値と、正解に対する相対値の中央値。計算は packages/nutrition(本番と同じ規則) |
| 処理時間 | 1 回の解析の時間の中央値・95 パーセンタイル(ミリ秒)。画面での待ち時間の目安 |
| 費用 | 応答のトークン数 × 確認した単価 × 為替(円)。1 食あたり・1,000 食あたりで示す |
| 安定性 | 同じ写真を 3 回送ったときの結果のばらつき(識別の一致率・重さの変動係数) |
| 不適切な出力 | 栄養値・診断・助言などスキーマにない出力を返した回数(スキーマで捨てるが、数は記録する) |

判断の目安(案):要確認率と栄養の誤差を主に見て、処理時間(中央値 10 秒以内)と費用で絞る。数値の基準は結果を見てから決める(先に決めない)。

## 5. 実行

```
npm run ai-eval                                  # mock(費用なし・外部に送らない)
node scripts/ai-eval/run.ts --dataset <path> --provider mock --repeats 3
```

- 実際のプロバイダは **まだ実装していない**(`PROVIDERS` に mock だけ)。指定するとエラーで止まる。
- 承認後に追加するときも、次の条件をコードで強制する:`--approved` の指定、料金の設定(確認日・出典つき)、実行前の見積もり × 1.5 が上限以内、実行中に上限へ達したら止める。
- API キーはリポジトリ・ログに置かない。評価用の別のキー(利用上限を設定したもの)を使う。

## 6. 予算(初期案:5,000 円)

- 上限 5,000 円(**承認待ち**)。想定:3 プロバイダ × 50 食 × 3 回 = 450 回。
- `scripts/ai-eval/budget.ts`:`planRun`(見積もり × 1.5 が上限以内でなければ実行しない)、`BudgetGuard`(実行中、次の 1 回の見積もりを足すと上限を超えるなら止める)。
- あわせて、各社の管理画面で利用上限(ハードリミット)を設定する(承認後)。

## 7. 承認が必要なこと(実行前)

1. 予算の上限(5,000 円案)と、評価用の API キーの用意(D-36)
2. 比べるプロバイダ(D-01 の候補)と、各社のデータの取り扱い条件の確認結果
3. データセットの作り方(協力者・撮影・秤量の手順)と、正解の食品番号の確認方法
4. 結果の判断の基準
